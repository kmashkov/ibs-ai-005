# HW-WEATHER-MASHKOV

# Проверка плана v1

Это проверка плана и матрицы тестирования, не реализации. Исходники, сборка и тесты не запускались; вердикт не подтверждает готовность кода. Для передачи Planner на v2 нужны следующие уточнения.

## Замечания

### CRIT-01 — HIGH: новый путь наследует рискованный fallback геокодирования

**Фрагмент:** «геокодирует город существующей логикой»; шаг 3: «Общий geocoding вынести в приватный helper без изменения его matching/ambiguous/not-found поведения».

**Контрпример:** текущий `OpenMeteoRiskService.assess` при отсутствии точного совпадения имени подменяет список кандидатов всеми ответами геокодера (`namedCandidates = exactMatches.length > 0 ? exactMatches : locations`). Для запроса `Dubia, United Arab Emirates`, если API вернёт один близкий результат `Dubai`, он станет единственным кандидатом и прогноз будет загружен. Для нового инструмента это автоматический выбор города, хотя запрос не разрешился однозначно. Старые инструменты при этом должны сохранить прежнее поведение.

**Исправление:** оставить resolver и поведение старых tools нетронутыми; определить отдельную для нового инструмента политику точного совпадения имени и всех указанных уточнений. Если точных кандидатов нет — вернуть controlled not-found; несколько точных — ambiguous. Не считать один неточный результат достаточным.

**Проверка закрытия:** мок геокодера возвращает единственный похожий, но не совпадающий город: новый tool отказывает без forecast. Отдельно проверить exact match, qualifier match, ambiguous и пустой результат, а также существующий тест/контракт старого `assess_weather_risk`.

### CRIT-02 — MEDIUM: не зафиксирован интерфейс между handler и методом поиска

**Фрагмент:** архитектура обещает «добавить отдельный метод поиска»; шаг 3 называет типы `SafeWindowSearchRequest`, `SafeWindowSearchResult` и «метод поиска», но не фиксирует его имя и сигнатуру. Handler должен вызвать новый метод, «если предоставленный risk service имеет новый метод».

**Контрпример:** `createServer` сейчас принимает объект с `assess(request)`. Без имени и точной сигнатуры Planner/Builder могут реализовать несовместимые варианты (`search`, `findSafeWindow`, аргумент с уже разобранными датами или без снимка `now`), а тип capability останется неясен.

**Исправление:** в v2 задать экспортируемый optional-интерфейс, например `findSafeWeatherWindow(request, now): Promise<...>`, указать, кто парсит даты и строит кандидатов, и какие discriminated outcomes возвращает сервис для not-found/ambiguous. Зафиксировать отдельный controlled ответ handler-а, если метод отсутствует.

**Проверка закрытия:** TypeScript build проверяет указанную сигнатуру; тест вызывает MCP handler с настоящим сервисом и с legacy stub, содержащим только `assess`.

### CRIT-03 — MEDIUM: время валидации и `fetched_at` имеют разные, неоговорённые clock seams

**Фрагмент:** «взять ровно один `now` из внедрённого clock»; handler должен передать снимок в сервис; `fetched_at` снимается «после успешного разбора этого ответа».

**Контрпример:** текущий `createServer` получает `weatherNow` из `weatherDependencies`, тогда как переданный или созданный по умолчанию `OpenMeteoRiskService` имеет собственный clock. При тестовом clock или переходе времени handler может разрешить интервал относительно одного `now`, а сервис повторно проверить его относительно другого. При этом `fetched_at` по смыслу должен отражать получение прогноза, а не снимок начала запроса.

**Исправление:** явно разделить одноразовый `requestNow` для валидации/генерации и `fetched_at` после успешного forecast; сервис не должен повторно валидировать поиск через свой clock. Указать, какой внедрённый clock формирует `fetched_at` и что он читается только после получения прогноза.

**Проверка закрытия:** тестовый clock выдаёт разные значения при последовательных чтениях; доказать, что граничная валидация использует только первый снимок, а `fetched_at` соответствует чтению после успешного ответа. При ошибке/таймауте результат и `structuredContent` отсутствуют.

### CRIT-04 — MEDIUM: не выбран и не проверяется горизонт параметра forecast-запроса

**Фрагмент:** план требует одним запросом покрыть весь поиск до `now + 120h`, но описание запроса ограничено словами «один hourly ряд» и повторным использованием validators. В текущем сервисе URL явно задаёт `forecast_days=6`.

**Контрпример:** проверка локального массива может случайно пройти на моках, тогда как запрос для интервала у конца пятисуточного горизонта фактически попросит меньший диапазон или будет полагаться на незафиксированное значение API по умолчанию. В плане не сказано, должен ли новый запрос явно сохранять `forecast_days=6` или вычислять горизонт.

**Исправление:** зафиксировать параметр/правило формирования URL для максимального допустимого интервала и проверить границу; не полагаться на API default. Если сохраняется `forecast_days=6`, обосновать, что оно покрывает UTC часы во всём разрешённом интервале.

**Проверка закрытия:** тест инспектирует URL и использует `now` около конца UTC-дня с `search_end` у границы `now+120h`; мок содержит последний час, пересекающий поиск. Отсутствие этого часа должно завершаться controlled error.

### CRIT-05 — MEDIUM: сценарий `+1ms` нельзя представить входной датой

**Фрагмент:** этап 1 обещает тест `end==now+120h` и «+1ms»; матрица повторяет `end=now+120h+1ms`. Входной формат при этом только `YYYY-MM-DDTHH:mm`.

**Контрпример:** при `now=12:00:00.001` дата с минутной точностью может обозначить `12:00:00` (на 1 мс раньше верхней границы) или `12:01:00` (на 59 999 мс позже), но не ровно `now+120h+1ms`. Такой тест не сможет построить требуемый аргумент через публичную строку.

**Исправление:** для публичного parser-теста выбрать минутно-представимую верхнюю границу и проверить ближайшее следующее допустимое значение строки. Если важен арифметический `+1ms`, проверять отдельно внутренний helper, принимающий `Date`, и не выдавать это за тест MCP-входа.

**Проверка закрытия:** тесты явно показывают вычисленные миллисекунды и проверяют обе соседние представимые минутные строки; нет фиктивного вызова parser-а со строкой, кодирующей миллисекунды.

### CRIT-06 — MEDIUM: генеративные проверки могут повторно использовать ошибочный comparator и не проверять production generator

**Фрагмент:** генеративная проверка сравнивает победителя с каждым элементом «по comparator» и проверяет containment каждого сгенерированного периода. Не указано, что наборы и окна проходят через production `buildCandidatePeriods`.

**Контрпример:** если oracle вызывает тот же `rankWindows`/comparator, который тестируется, ошибка порядка рисков или факторов воспроизведётся и в ожидаемом сравнении. Если PRNG создаёт только заранее валидные искусственные периоды, дефект генератора, выпускающий окно за `search_end`, останется незамеченным.

**Исправление:** вычислять ожидаемого победителя независимой тестовой функцией, буквально реализующей кортеж из требований; для containment генерировать входные интервалы и длительности, вызывать production generator, затем проверять каждый выданный результат. Перестановку применять к одному и тому же набору оценок.

**Проверка закрытия:** seeded-тест падает при намеренно инвертированном ключе comparator-а и при мутации границы генератора; все три инварианта покрывают результат production-функций.

### CRIT-07 — MEDIUM: совместимость legacy stub проверяется не полностью

**Фрагмент:** план говорит, что stub `{ assess(...) }` сохраняет работу старых tools и что вызов нового tool при отсутствии метода даёт controlled unavailable; в матрице указано только «legacy stub» и старые tools.

**Контрпример:** сервер может успешно создаться и старые инструменты работать, но вызов зарегистрированного `find_safe_weather_window` на том же stub бросит `TypeError` или попадёт в generic error с нестабильным payload.

**Исправление:** отдельно зафиксировать ожидаемый результат вызова нового tool на legacy stub: `isError:true`, понятный контролируемый текст, отсутствие `structuredContent`, без внешних запросов. Проверить создание сервера и старые методы тем же stub-ом.

**Проверка закрытия:** MCP test выполняет оба старых вызова и новый вызов на `{assess}`, подтверждает вышеуказанный контракт и отсутствие необработанного исключения.

### CRIT-08 — LOW: план не перечисляет все существующие утверждения о списке tools, которые надо обновить

**Фрагмент:** этап 4 упоминает «tools/list содержит 4» и говорит обновить «ровно ожидание count с 3 на 4» в `compare-weather-windows.test.mjs`.

**Контрпример:** текущие тесты проверяют точный массив имён в `compare-weather-windows.test.mjs` и `mcp-health.test.mjs`, а в `mcp-health.test.mjs` после ошибки отдельно ожидают `tools.length === 3`. Замена только числового ожидания не обновит список имён; частичное изменение оставит CI красным.

**Исправление:** перечислить все текущие assertions `tools/list`: точный список из четырёх имён в обоих файлах и пост-ошибочную длину 4. Проверять имена и сохранность трёх старых tools, а не только число.

**Проверка закрытия:** целевые команды запускают оба тестовых файла; все проверки списка подтверждают ровно три старых имени плюс новый tool до и после невалидного вызова.

### CRIT-09 — LOW: ручная проверка обозначена сценарием, но не воспроизводимой командой

**Фрагмент:** этап 5: «Ручной Inspector вызов сделать с датами…»; матрица говорит «MCP Inspector», не называя способ запуска и минимальную запись доказательств.

**Контрпример:** из чистого состояния непонятно, запускать ли Inspector из `dist` или через `tsx`; пакетный скрипт `npm run inspect` использует `node dist/index.js`, значит до вызова нужен успешный build. Одного описания «успех/отказ» недостаточно, чтобы отличить запланированный пример от фактического.

**Исправление:** зафиксировать последовательность `npm run ci`, затем `npm run inspect` из `weather-mcp/`; в `verification.md` сохранить фактические аргументы с вычисленными датами, реальный ответ/ошибку и время вызова, без секретов. Отказ города выбирать только после исправления политики геокодирования из CRIT-01.

**Проверка закрытия:** другой человек может выполнить указанные команды; verification содержит один реально выполненный success и один реально выполненный controlled отказ, а не ожидаемые ответы.

## Итог

План хорошо отделяет новый поиск от старых контрактов и покрывает ключевые временные, риск- и forecast-границы. Перед реализацией нужно закрыть CRIT-01—CRIT-07 в v2; CRIT-08 и CRIT-09 уточнить там же, чтобы целевые команды и ручное доказательство были однозначны. Это заключение относится только к плану v1.
