# Вопросы и предложения для одобрения v2

Критичных отсутствующих бизнес-правил не выявлено. Следующие проектные решения Planner должен явно внести в `implementation-plan-v2.md` для одобрения пользователем до реализации.

1. **Граница «в будущем».** Предлагается требовать `search_start > now` для нового инструмента. Текущий helper старых инструментов допускает `start == now`; их поведение менять нельзя. Решение определяет граничную валидацию нового входа.
2. **Интервал без кандидатов.** Предлагается возвращать контролируемую ошибку без частичного `structuredContent`. План должен назвать выбранный MCP error contract.
3. **Окна с HIGH.** Предлагается всегда выбирать лучший кандидат по сортировке, даже если все кандидаты HIGH, и честно вернуть `recommendation: CANCEL`; слово «лучший» само по себе не означает безопасный.
4. **Количество факторов.** Использовать `factors.length` из существующей оценки риска. Код создаёт одну запись фактора на каждую пару час+метрика; новый алгоритм не вводит иной подсчёт.
5. **Границы интервалов.** Предлагается трактовка `[start, end)`: окно может начинаться ровно в `search_start` и завершаться ровно в `search_end`.
6. **Контракт `structuredContent`.** Поля имени города, `source`, `fetched_at` и числа проверенных кандидатов обязательны по заданию; предлагаемые имена полей для выбранного окна, альтернатив и счётчика зафиксировать в v2 как стабильную схему.
7. **Выравнивание полного часа.** Предлагается старт в `:00` московского времени с шагом один час. Москва использует UTC+3, поэтому :00 MSK и :00 UTC совпадают; это не отдельный бизнес-блокер.

Одобрение implementation-plan-v2.md разрешает перейти к реализации в указанной области. До такого одобрения исходный код менять нельзя.
