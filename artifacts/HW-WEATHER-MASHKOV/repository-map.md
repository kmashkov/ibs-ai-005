## Модули и ответственность

- `weather-mcp/src/index.ts:11-13,186-203` — MCP wiring, схема входа, преобразование ошибок и ответы `content`/`structuredContent`; здесь уже внедрены `get_weather`, `assess_weather_risk`, `compare_weather_windows` (`:205-363`).
- `weather-mcp/src/time.ts:12-50` — разбор московского `YYYY-MM-DDTHH:mm`, перевод MSK→UTC, единичная проверка периода и пересечения часов. Сейчас helper проверяет начало и конец одного рабочего окна (`:39-45`); для поиска нужен отдельный разбор/валидация границ всего поискового диапазона относительно одного `now`.
- `weather-mcp/src/open-meteo.ts:51-139,142-235` — геокодирование, один запрос почасового прогноза на оценку, проверка целостности данных, кэш и `OpenMeteoRiskService.assess`. Неоднозначный город возвращает варианты до forecast (`:185-210`); сбои/неполный прогноз превращаются в контролируемые ошибки (`:152-167,80-139`).
- `weather-mcp/src/risk.ts:18-58` — единственная реализация риск-порогов; `assessRisk` возвращает уровень, рекомендацию и фактор для каждой нарушенной метрики каждого часа.
- `weather-mcp/src/cache.ts:1-39` — нормализация города и ограниченный in-memory cache с TTL 10 минут.
- `weather-mcp/src/health.ts:3-20` — необязательный локальный `/health`, не относится к расчёту погодных окон.

## Поток данных текущей задачи

1. MCP принимает `city`, `work_type`, московские `search_start`/`search_end` и целое `duration_hours` 1..8; проверка должна отклонять некорректные значения до внешних запросов. Источник требований: `ЗАДАНИЕ.md:24-54`, уточнённая спецификация `artifacts/HW-WEATHER-MASHKOV/task-spec.md:7-25,51-67`.
2. Один снимок часов `now` задаёт границы: **весь поисковый интервал** должен находиться в будущем и не выходить за `now + 5 суток` (`task-spec.md:69-77` уточняет это правило). Кандидаты строятся с шагом час от полного часа по трактовке, указанной как предложение в `task-spec.md:43-49`; эта трактовка и точная схема ответа подлежат согласованию.
3. Сервис разрешает город через Geocoding API; неизвестный или неоднозначный результат останавливает путь до прогноза. После однозначного результата одним UTC hourly forecast нужно покрыть **весь поисковый интервал**, в том числе крайние часы, которые не входят ни в одно окно-кандидат; проверка полноты не должна ограничиваться только кандидатными периодами. Текущий шаблон параметров запроса и обработка города/прогноза: `open-meteo.ts:180-219`; Planner определит подходящее расширение сервиса.
4. Почасовые значения для каждого кандидата передаются в общий `assessRisk` (`risk.ts:18-58`), затем окна сортируются по уровню риска, числу записей факторов и времени начала — предложенный детерминированный ключ в `task-spec.md:45-49`. Успех возвращает победителя и до трёх альтернатив; ошибка прогноза не должна возвращать частичные окна (`task-spec.md:56-63`).

## Гипотезы и пробелы

- `task-spec.md` помечает выравнивание на `:00` по московской шкале, полуоткрытость окон и подсчёт каждого `RiskFactor` предложениями к подтверждению (`:43-49`). Их нельзя считать утверждёнными контрактами до решения владельца задачи.
- Прогноз должен покрывать весь поисковый интервал, хотя существующий `OpenMeteoRiskService.assess` извлекает и проверяет лишь часы одного рабочего периода (`open-meteo.ts:80-139,169-235`). Одного повторного вызова `assess` на каждого кандидата будет недостаточно и нарушило бы требование одного forecast запроса; способ расширения сервиса оставлен Planner.
- Рабочая спецификация называет `weather-mcp/README.md` целевым README; файла `README.md` в корне проекта нет.
