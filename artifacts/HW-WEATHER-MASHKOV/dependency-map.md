# HW-WEATHER-MASHKOV

# Карта зависимостей

## Среда выполнения и инструменты

- `weather-mcp/package.json`: пакет `weather-mcp@1.0.0`, ESM (`type: module`), Node.js `>=20`; проектная toolchain — TypeScript, MCP SDK, Zod. Оркестратор сообщил о локальных Node.js `v22.23.0` и npm `10.9.8`; это совместимо с минимальным требованием manifest.
- `weather-mcp/tsconfig.json`: TypeScript `NodeNext`, target `ES2022`, строгая типизация (`strict`), исходники `src/**/*.ts`, результат в `dist`.
- `weather-mcp/package-lock.json`: lockfile v3 фиксирует разрешённые версии. `Dockerfile` использует `node:24-alpine` в build и runtime stages и `npm ci`; это отдельная среда от сообщённой локальной Node 22.
- Скрипты `npm run build`, `npm test`, `npm run ci` указаны в manifest. Ничего из них в рамках этого анализа не запускалось; наличие `node_modules`/`dist` не подтверждает успешную сборку.

## Прямые зависимости задачи

- `@modelcontextprotocol/server`: объявлено `^2.0.0`, зафиксировано `2.0.0` в lock; MCP-регистрация инструмента/ответы `structuredContent` и `isError` в `src/index.ts`.
- `zod`: объявлено `^4.0.0`, зафиксировано `4.6.5`; используется как `zod/v4` в `src/index.ts` для input schema. Новая схема может использовать имеющуюся зависимость.
- Новых npm-пакетов для описанной задачи по имеющимся источникам не требуется: временная логика, ранжирование и HTTP реализованы приложением.

## Транзитивные зависимости

- `@modelcontextprotocol/server@2.0.0` тянет `@modelcontextprotocol/core@2.0.0`, который объявляет peer dependency `zod@^4.2.0` и runtime dependency `zod@^4.2.0`. Зафиксированный `zod@4.6.5` удовлетворяет обоим диапазонам.
- Для разработки/ручной MCP-проверки объявлены `@modelcontextprotocol/client@^2.0.0` (lock `2.0.0`) и `@modelcontextprotocol/inspector@^2.7.0` (lock `2.7.0`); они не нужны runtime контейнеру (`npm ci --omit=dev`). Inspector в lock требует Node `>=22.19.0`, что выполняется для сообщённого Node 22.23.0 и образа Node 24.
- Остальные закреплённые инструменты: `@types/node@24.10.0`, `tsx@4.23.15`, `typescript@5.9.3`. Типы Node 24 скомпилированы при target ES2022; фактическая проверка сборкой здесь не выполнялась.
- В lock присутствует транзитивный `undici@8.11.0` как dev-зависимость инструментария; приложение использует глобальный `fetch` и `AbortSignal.timeout`, отдельный import `undici` в `src` не найден.

## Внешние сервисы и данные

- Open-Meteo Geocoding API (`https://geocoding-api.open-meteo.com/v1/search`) разрешает введённый город; `src/open-meteo.ts` проверяет ответ, не выбирает неоднозначный город, ограничивает запрос пятью вариантами и локализует язык по алфавиту ввода.
- Open-Meteo Forecast API (`https://api.open-meteo.com/v1/forecast`) используется для почасовых `temperature_2m`, `precipitation_probability`, `wind_speed_10m`, с единицами ветра `ms` и `timezone=UTC` в сервисе оценки риска. Результат проверяется на корректность/полноту всех почасовых значений.
- Для новой функции условие требует один forecast-запрос на весь поисковый интервал. Нынешний риск-сервис всегда задаёт `forecast_days=6`; его доступность на требуемый горизонт до пяти суток и покрытие любого поиска, чей конец укладывается в допустимый горизонт, надо сохранить/подтвердить конкретной реализацией запроса.
- Используется глобальный `fetch`, без отдельной БД, очереди или внешнего кэша. Секрет Open-Meteo не требуется по README.

## Совместимость версий

- Объявленный минимум Node `>=20` согласован с `AbortSignal.timeout` и глобальным `fetch`, используемыми в исходниках; Docker запускается на Node 24. MCP SDK `2.0.0` и Zod `4.6.5` согласованы по lock.
- Локальный Node `22.23.0` проходит ограничение Inspector `>=22.19.0`; `npm 10.9.8` работает с lockfile v3. Docker `npm ci` воспроизводит lock в обеих стадиях, но Docker-образ в этом задании не собирался.
- `src/time.ts` трактует ввод без смещения как фиксированный MSK UTC+3, проверяет календарное время и границы периода; `src/open-meteo.ts` переводит прогноз в UTC. Поскольку используемый сдвиг MSK фиксирован и равен UTC+3, целочасовое выравнивание по epoch сохраняет минуту :00 при переводе между шкалами. Москва не использует сезонный переход в текущей реализации, однако правило надо зафиксировать для календарной границы и корректности формата/вывода.

## Риски и требуемые проверки

- `src/open-meteo.ts`: таймаут внешнего запроса 5 секунд (`AbortSignal.timeout(REQUEST_TIMEOUT_MS)`); `src/index.ts` для существующего `get_weather` — 10 секунд. Новый путь должен иметь единый контролируемый отказ при ошибке/таймауте/плохом ответе и не отдавать частичные окна.
- `src/cache.ts`: кэш в памяти процесса, TTL 10 минут, максимум 500 записей, удаление просроченных и вытеснение самой старой записи. Существующие сервисы кэшируют успешные оценки; неизвестные/неоднозначные результаты риска в кэш не помещаются. Повторно возвращённая из кэша оценка сохраняет исходный `fetched_at`; при повторном использовании кэша это время не обновляется.
- `src/risk.ts`: единственный источник порогов и факторов (каждая запись — час+метрика); повторное использование `assessRisk` важно, иначе возможен дрейф tie-break и уровней. Пороговая логика не различает `work_type`.
- `src/time.ts` проверяет одиночный рабочий период относительно `now` и `now+5d`. Вход новой функции — весь поисковый интервал: он должен быть валидирован относительно одного снимка `now`, целиком в будущем и в пределах пяти суток. Генерация кандидатов только внутри допустимой части не должна молча принимать некорректный поисковый интервал.
- Обязательные проверки по задаче (сборка/тесты, ручной MCP вызов, устойчивость ранжирования, полный прогноз одним запросом) остаются работой следующих этапов; эта карта не утверждает, что они выполнены.

## Гипотезы и пробелы

- `task.json.task_key`, `external_id` и переданный ключ совпадают: `HW-WEATHER-MASHKOV`. В спецификации остаются проектные предложения под одобрение v2: выравнивание старта по московскому часу, подсчёт `RiskFactor`, окончательная форма ответа и поведение при нуле окон. Их нельзя выводить из зависимостей.
- Требуется убедиться, что Open-Meteo отдаёт полный часовой ряд на интервал, допустимый существующим `forecast_days=6`, учитывая UTC-границы запроса и максимум в пять суток по Москве. Ни сетевой вызов, ни актуальный лимит провайдера в этом анализе не проверялись.
- Уязвимости, актуальная поддержка пакетов и лицензии отдельно не проверялись; lock содержит license-метаданные, но карта не трактует их как аудит.
