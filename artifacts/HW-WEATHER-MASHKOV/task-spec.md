HW-WEATHER-MASHKOV

# Спецификация задачи

## Цель

Добавить в локальный MCP-сервер `weather-mcp` инструмент `find_safe_weather_window`, который получает московский интервал поиска, строит допустимые почасовые окна заданной целочасовой длительности, оценивает их по погодному риску и возвращает лучший вариант и до трёх альтернатив.

## Подтверждённые требования из ЗАДАНИЕ.md

- Новый MCP-инструмент называется `find_safe_weather_window`.
- Вход содержит `city`, `work_type`, `search_start`, `search_end`, `duration_hours`.
- `search_start` и `search_end` задаются по Москве; образец формата — `YYYY-MM-DDTHH:mm`.
- `duration_hours` — целое число от 1 до 8 включительно.
- Начала кандидатов идут каждый полный час; каждое целое окно должно полностью помещаться в интервал поиска.
- Весь интервал поиска [search_start, search_end] должен находиться в будущем и в пределах пяти суток от текущего момента.
- Порядок уровней риска: `LOW < MEDIUM < HIGH`.
- При одинаковом уровне риска лучше кандидат с меньшим количеством факторов; при полном равенстве лучше более раннее окно.
- Ответ включает выбранное окно и не более трёх альтернатив.
- Количество проверенных кандидатов, город, источник и время получения данных входят в `structuredContent`.
- Неоднозначный или неизвестный город не разрешается выбирать автоматически.
- При сбое Open-Meteo возвращается контролируемая ошибка без частичного результата.
- Почасовой прогноз для всего интервала запрашивается одним внешним запросом.
- `get_weather`, `assess_weather_risk` и `compare_weather_windows` сохраняют прежнее поведение и контракты.
- Требуются читаемое разделение получения прогноза, построения кандидатов и ранжирования, общие пороги риска без копирования, Zod-схема входа, стабильный `structuredContent` и обновлённый README.
- Обязательный минимум проверки — `npm run ci`; затем требуется ручной вызов через MCP Inspector или подключённый Codex.
- `verification.md` должен содержать команды, результат сборки, число прошедших тестов, два примера вызова (успех и контролируемый отказ) и известные ограничения; секреты и токены исключаются.
- Дополнительный критерий: property-based или генеративная проверка, что выбранный вариант не хуже любой альтернативы по правилам сортировки, окна лежат внутри интервала, а перестановка кандидатов не меняет победителя за исключением полного равенства.
- Сдаваемые результаты включают ссылку/архив/diff проекта, каталог артефактов, главный промпт и рефлексию на 5–10 предложений по четырём заданным темам.

## Подтверждённые факты о текущем проекте

- Сервер реализован на Node.js/TypeScript, использует MCP SDK и Zod 4; команды объявлены в `weather-mcp/package.json`, включая `npm run ci` = сборка TypeScript и Node test runner.
- Текущие инструменты регистрируются в `weather-mcp/src/index.ts`. Ошибки MCP возвращаются с `isError: true`; структурированный payload в успешных ответах выдаётся через `structuredContent`.
- `parseWorkPeriod` в `src/time.ts` принимает только `YYYY-MM-DDTHH:mm`, трактует значение как MSK (UTC+3), проверяет календарную дату, старт не раньше переданного `now` и окончание не позже `now + 5 суток`. Текущий helper допускает дробную длительность для старых инструментов; новый инструмент по заданию обязан требовать integer 1..8.
- `intersectsHour` рассматривает каждый UTC-час, который пересекает полуоткрытый период `[start, end)`. `src/open-meteo.ts` получает погодный прогноз в UTC; проверяет, что данные полны для всего оцениваемого периода, и при нехватке часа бросает `WeatherDataError`.
- `assessRisk` в `src/risk.ts` создаёт фактор для каждой почасовой метрики за пределами порога. Итоговый риск — максимальный уровень факторов по часам; без факторов — `LOW`. Фактор содержит время, метрику, значение и уровень.
- Действующие пороги (зафиксированы в `src/risk.ts` и `test/risk-time.test.mjs`): осадки `>=40%` MEDIUM, `>=70%` HIGH; ветер `>=10 м/с` MEDIUM, `>=15 м/с` HIGH; температура `<-5` или `>32°C` MEDIUM, `<-15` или `>40°C` HIGH. Рекомендации соответствуют LOW/PROCEED, MEDIUM/REVIEW, HIGH/CANCEL.
- `OpenMeteoRiskService` в `src/open-meteo.ts` сначала геокодирует город, не выбирает неоднозначный автоматически, при неоднозначности отдаёт до пяти вариантов; прогноз запрашивает после однозначного разрешения города. Запросы имеют таймаут, ошибки преобразуются в контролируемые погодные ошибки. Успешная оценка содержит найденное местоположение, часовой пояс, период UTC, почасовые данные, риск, факторы, источник `Open-Meteo` и `fetched_at`.
- `compare_weather_windows` в `src/index.ts` ранжирует только по risk_level, а при равном уровне сохраняет оба окна как ничью. Для новой функции условие явно задаёт дополнительные ключи сортировки: число факторов и раннее время.
- Исходные тесты проверяют пороги/границы, московское преобразование, ошибки неполного прогноза и геокодирования, таймауты, прежний контракт сравнения. Команды сборки и тестирования в рамках анализа не запускались.

## Предложения для реализации, требующие подтверждения трактовки

1. Предложение: считать «полным часом» начало с минутами `00` по Москве; генерировать старты от первого такого момента не раньше `search_start`, затем с шагом ровно 60 минут. MSK = UTC+3 без сезонного сдвига, поэтому выравнивание по :00 MSK и UTC совпадает.
2. Считать окно полуоткрытым `[start, end)`: оно допустимо, если `start >= search_start` и `end <= search_end`. Это согласуется с существующим `intersectsHour` и включает конец интервала как допустимую границу завершения.
3. Считать числом факторов `factors.length` для каждого окна: текущий `assessRisk` формирует отдельную запись RiskFactor на каждую пару час+метрика.
4. Предложение: ранжировать по кортежу `(risk rank, factors.length, start timestamp)` по возрастанию и среди всех кандидатов, включая HIGH, возвращать лучшего по сортировке с его фактической рекомендацией (HIGH остаётся CANCEL). В `structuredContent` вернуть минимум идентификатор/локальное начало/конец/длительность/риск/рекомендацию/факторы для выбранного и альтернатив; точные имена полей и контролируемое поведение при отсутствии кандидатов Planner определит явно в v2.
5. Использовать существующую оценку риска и её пороги для всех `work_type`; сейчас тип работы принимается, но никак не влияет на алгоритм. Специальные пороги по типам работ отсутствуют в предоставленном условии и исходном коде.

## Критерии приёмки

1. MCP `tools/list` содержит `find_safe_weather_window` и сохраняет все три существующих инструмента.
2. Валидный вход с `duration_hours` 1 и 8 проходит схему; значения 0, 9, дробное, строка, неизвестный `work_type`, пустой/слишком длинный город и лишние поля (если схема использует strict object) отклоняются контролируемой ошибкой до внешнего запроса.
3. Время разбирается по московскому времени и некорректные/несуществующие даты отклоняются; кандидаты имеют часовой шаг согласно утверждённой трактовке.
4. Весь поисковый интервал `[search_start, search_end]` валиден только если он целиком в будущем и целиком внутри горизонта `[now, now + 5 суток]` (строгость нижней границы нового инструмента — предложение `search_start > now`, ожидает одобрения v2). Каждый кандидат дополнительно полностью помещается в интервал поиска; если кандидатов нет, предложение — контролируемая ошибка без частичного результата.
5. Для успешного сценария выполняется ровно один внешний forecast-запрос, охватывающий весь интервал поиска. Геокодирование города до прогноза и поведение при неоднозначности наследуются от существующего сервиса; их конкретная организация — проектное решение.
6. Неизвестный город и неоднозначный город приводят к понятной контролируемой ошибке/ответу без автоматически выбранной локации и без частичного набора окон.
7. Ошибка, таймаут, некорректный или неполный ответ Open-Meteo даёт контролируемую ошибку без победителя, альтернатив и частичного `structuredContent`.
8. Результаты сортируются детерминированно по риску, `factors.length` и времени старта; возвращается лучший кандидат и не более трёх следующих. При меньшем числе допустимых кандидатов список короче; проверенное количество равно размеру множества допустимых кандидатов, отправленных на ранжирование.
9. `structuredContent` стабильно содержит список выбранного/альтернатив, число проверенных кандидатов, разрешённый город, источник `Open-Meteo` и время получения данных; точная схема и единицы времени должны быть утверждены до реализации.
10. Факторы и уровни риска соответствуют существующим центральным порогам `assessRisk`; новые копии порогов не вводятся. `work_type` не меняет риск, пока отдельные правила не заданы.
11. Поведение/структурированные ответы существующих `get_weather`, `assess_weather_risk`, `compare_weather_windows` не меняются; регрессионный `npm run ci` завершается успешно.
12. README описывает новый инструмент, параметры, сортировку, временную семантику и примеры структуры результата.
13. Проверки включают граничные случаи временного окна, сортировку по каждому ключу, 0/1/3/4+ допустимых кандидатов, нулевых факторов/одинаковые риски, неизвестный/неоднозначный город, ошибку прогноза и единственный запрос прогноза. Для дополнительного задания property-based/генеративные проверки доказывают три указанных инварианта.
14. Ручная проверка через Inspector/Codex сохраняет два реальных примера вызова: успешный результат и контролируемый отказ; в verification явно записаны команды и число тестов.
15. Рефлексия содержит 5–10 предложений и отвечает на все четыре пункта задания.

## Границы и ограничения

- На данном этапе разрешены анализ и подготовка артефактов; кодирование запрещено до явного одобрения пользователем `implementation-plan-v2.md`.
- В этом проектном проходе исходный код не меняется. При реализации область ограничивается новым инструментом и непосредственно нужными тестами/документацией; расширение контрактов старых инструментов запрещено.
- Не добавлять риск-правила по типам работ без отдельного подтверждения.
- Не подменять реальные сборку, тесты или ручные MCP-вызовы утверждениями; до выполнения они остаются планируемыми проверками.
- Не включать секреты, токены и `.env` в артефакты или сдаваемый пакет.
- Пятисуточный горизонт и «будущее» проверяются для всего поискового интервала относительно единого снимка `now` на запрос. Строгость сравнения `search_start` с `now` предлагается как `>` для нового инструмента; старые инструменты сохраняют действующее `>=`.
- Внешняя зависимость — Open-Meteo geocoding и forecast API; сетевые сбои должны оставаться контролируемыми.
