# Отчёт о готовности Weather MCP к передаче

Дата аудита: 29.09.2026  
Проверенная ревизия: `c11a57b443ccf688c58c8add975ccfe27131a2f9`  
Область аудита: `artifacts/HW-DOCS-MASHKOV/` с проверкой по исходникам, тестам, manifest/lockfile, Dockerfile и артефактам задачи `HW-WEATHER-MASHKOV`.

## Итог

**Проект технически работоспособен, но к полностью автономной передаче другой команде пока не готов.**

Код можно передавать для продолжения разработки: TypeScript собирается, локальный `npm run ci` прошёл, 38 из 38 тестов успешны, основные контракты описаны и защищены. Для передачи эксплуатации или новому владельцу без устного сопровождения не хватает воспроизводимого bootstrap/runbook, точного статуса поставки, полного описания интеграции и согласованной версии требований к Node.js. Docker-сценарий не подтверждён.

Отдельный организационный блокер: текущая ветка `codex/hw-weather-mashkov` на два документационных коммита опережает `origin/codex/hw-weather-mashkov`. Следовательно, содержимое `HW-DOCS-MASHKOV` пока нельзя считать опубликованным в upstream. Ветка также не является `main`; при передаче необходимо явно указать целевую ветку и ревизию либо подготовить актуальный архив.

## Неточности и противоречия

### Major

1. **Не согласованы требования к версии Node.js.** `HW-DOCS-MASHKOV/README.md` и `package.json` заявляют Node.js `>=20`, но зафиксированный `@modelcontextprotocol/inspector@2.7.0` требует Node.js `>=22.19.0` (`package-lock.json`). Для runtime это не обязательно проблема, но инструкция не разделяет требования сервера, CI и Inspector. Проверка на Node 20 не выполнялась.

2. **Канонический `weather-mcp/README.md` привязан к чужой машине.** Установка содержит путь `C:\Users\boria\Desktop\AI-005\weather-mcp`, а пример Codex-конфигурации предполагает схожую структуру. Краткий README в `HW-DOCS-MASHKOV` переносим, но два README дают новой команде разные по качеству инструкции.

3. **Документация существует локально, но ещё не опубликована в upstream.** HEAD опережает tracking branch на два коммита. Передача ссылкой на текущую удалённую ветку потеряет пакет `HW-DOCS-MASHKOV`.

### Minor

1. **Область кеширования описана слишком широко.** Формулировка `CONTEXT.md` о «результатах оценки погоды» создаёт впечатление общего кеша. Фактически `get_weather` и `assess_weather_risk` имеют отдельные in-memory кеши по 500 записей; `compare_weather_windows` использует путь `assess`; `find_safe_weather_window` кеш не использует.

2. **Формулировка «по худшему часовому фактору» неточна.** Итоговый уровень действительно определяется максимальным уровнем всех факторов, но вторичная сортировка использует общее число факторов во всех затронутых часах, а не один худший фактор.

3. **Граница настоящего времени описана по-разному.** `weather-mcp/README.md` называет окна `compare_weather_windows` будущими, однако `parseWorkPeriod` допускает `start_at == now` и запрещает только старт раньше `now`. Корректная формулировка: «не раньше текущего момента».

4. **Инструкция «каждый блок выполняется из корня проекта» двусмысленна.** Команды фактически переходят в `weather-mcp/`; проще один раз потребовать открыть эту директорию и далее выполнять `npm ci`, `npm run ci`, `npm start`.

5. **Правила изменений не до конца определяют инфраструктурные файлы.** `AGENTS.md` разрешает `src/`, `test/` и документацию, одновременно требуя согласования зависимостей. Не сказано, можно ли после согласования менять `package.json`, lockfile, Dockerfile и конфигурацию запуска.

6. **Статус процесса не совпадает с ожиданием полной передачи.** Основная задача находится в состоянии `VERIFIED`, а не `DOCUMENTED`/`RELEASED`. Для учебной реализации это допустимо, но не подтверждает готовность эксплуатации или выпуска.

## Какой информации не хватает

### Для установки и запуска

- как получить проект: URL/ветка/tag/commit либо точное имя передаваемого архива;
- bootstrap из чистого checkout: проверка версий, `npm ci`, `npm run ci`, `npm start`;
- раздельная матрица версий: runtime/build/tests и MCP Inspector;
- готовый переносимый пример подключения к Codex/другому MCP-клиенту без персональных путей;
- явное указание, что тесты используют контролируемые ответы, а реальная работа требует доступа к Open-Meteo.

### Для понимания и изменения

- краткая карта модулей и поток данных: `index.ts` → `open-meteo.ts` → `time.ts`/`risk.ts` → MCP response;
- ссылка из handoff-пакета на полные схемы входа/выхода и варианты ошибок всех четырёх инструментов;
- точное описание различий resolver-ов: legacy fuzzy fallback у `assess_weather_risk` и strict exact match у `find_safe_weather_window`;
- политика изменения зависимостей, lockfile, Dockerfile и публичных контрактов;
- перечень актуальных известных проблем и технического долга с приоритетами.

### Для эксплуатации

- runbook запуска, остановки, диагностики и восстановления;
- поведение `HEALTH_PORT`: допустимый диапазон, bind на `127.0.0.1`, недоступность endpoint снаружи контейнера без изменения bind;
- наблюдаемость: формат и место логов, метрики, рекомендуемый мониторинг, отсутствие persistent state;
- политика retry/rate-limit для Open-Meteo и ожидаемое поведение при длительной недоступности;
- подтверждённый Docker build/smoke-test или явное исключение Docker из поддерживаемых способов запуска;
- владелец, канал поддержки, политика версий и совместимости;
- лицензия/условия передачи, если проект передаётся за пределы учебной или внутренней команды.

### Для доказательства качества

- дата, среда и ревизия последнего CI прямо в handoff-пакете;
- ссылка на `artifacts/HW-WEATHER-MASHKOV/verification.md` и `review.json`;
- явное разделение проверок: локальные unit/contract tests, ручной MCP Inspector, реальный Open-Meteo, Docker;
- статус удалённого CI: workflow в репозитории отсутствует, `npm run ci` является только локальной командой.

## Что нужно исправить

### P0 — до передачи

1. Выбрать канал поставки: запушить текущую ветку, слить её в согласованную ветку либо собрать новый архив. Зафиксировать commit SHA и состав поставки.
2. Убрать персональные абсолютные пути из `weather-mcp/README.md`; дать bootstrap из чистого checkout и переносимый пример MCP-конфигурации.
3. Разделить требования к Node.js: минимум для runtime/build/tests и `>=22.19.0` для текущего Inspector. Либо зафиксировать единый поддерживаемый минимум Node.js 22.19+ и проверить его в CI.
4. Явно указать статус поставки: локальный сервис, production deploy не предусмотрен; Docker пока не является подтверждённым сценарием.

### P1 — для автономной работы новой команды

1. Уточнить `CONTEXT.md`: область каждого кеша, отсутствие кеша у поиска, алгоритм вычисления риска и legacy/strict различия геокодинга.
2. Добавить краткую карту модулей, таблицу контрактов инструментов и ссылку на полную документацию.
3. Добавить runbook и troubleshooting для STDIO, Open-Meteo, `HEALTH_PORT`, Inspector и типовых controlled errors.
4. Внести в handoff-пакет проверяемый статус: ревизия, дата CI, `38/38`, ручной Inspector из `verification.md`, Docker — `not verified`.
5. Уточнить в `AGENTS.md` правила изменения manifest/lockfile/Dockerfile и требуемое согласование.

### P2 — желательно

1. Добавить удалённый CI с `npm ci` и `npm run ci` на поддерживаемых версиях Node.js.
2. Добавить Docker smoke-test и проверку health endpoint.
3. Зафиксировать ownership, поддержку, версионирование и лицензию.
4. Добавить метрики внешних запросов, latency, ошибок и cache hit/miss.

## Финальный вердикт

**Сейчас: NO-GO для полной передачи ответственности, GO с оговорками для внутренней передачи кода/учебного продолжения.**

После закрытия P0 проект можно передавать другой команде как локальный MCP-сервис для разработки и тестирования. Для передачи эксплуатации необходимо также закрыть P1, подтвердить поддерживаемый способ запуска и определить владельца.
