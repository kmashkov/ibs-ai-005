# Контекст Weather MCP

## Реализовано

- MCP-сервер на Node.js и TypeScript с использованием MCP SDK; работает через STDIO. Диагностика идёт в STDERR, STDOUT зарезервирован под JSON-RPC.
- Доступны четыре инструмента: `get_weather` (текущая погода и прогноз на 1–7 дней), `assess_weather_risk` (почасовая оценка работ), `find_safe_weather_window` (поиск рабочего окна) и `compare_weather_windows` (сравнение двух окон).
- Геокодирование и прогноз поступают из Open-Meteo; API-ключ не требуется. Сетевые ошибки, некорректные ответы и неполный прогноз приводят к контролируемым ошибкам.
- Для `assess_weather_risk` выбирается худший уровень среди всех затронутых почасовых факторов. Пороги: `HIGH` — осадки ≥70%, ветер ≥15 м/с, температура ниже −15 °C или выше 40 °C (`CANCEL`); `MEDIUM` — осадки ≥40%, ветер ≥10 м/с, температура ниже −5 °C или выше 32 °C (`REVIEW`); иначе `LOW` (`PROCEED`).
- Время для `assess_weather_risk`, `find_safe_weather_window` и `compare_weather_windows` вводится с публичной меткой `Europe/Moscow` (формат `YYYY-MM-DDTHH:mm`). Реализация преобразует его фиксированным смещением UTC+3 и не обрабатывает правила произвольных часовых поясов. Время факторов почасового прогноза — UTC.
- `assess_weather_risk`, `find_safe_weather_window` и оба окна `compare_weather_windows` ограничены горизонтом прогноза в пять суток от текущего момента. Поиск разрешает город только при точном совпадении нормализованного имени и всех уточнений региона/страны. При нескольких точных совпадениях возвращаются варианты; автоматического выбора нет. Для оценки риска неоднозначность также возвращается списком вариантов.
- Внешние запросы ограничены таймаутом: 10 секунд для `get_weather` и 5 секунд для риск-сервиса, используемого `assess_weather_risk`, `find_safe_weather_window` и `compare_weather_windows`.
- Результаты оценки погоды кешируются в памяти процесса на 10 минут; кеш ограничен 500 записями на экземпляр.
- HTTP health endpoint `GET /health` запускается только при заданном `HEALTH_PORT`.

## Архитектурные решения

- STDIO оставлен основным транспортом MCP, поэтому обычный вывод процесса не засоряет канал JSON-RPC. Health endpoint — отдельная опциональная HTTP-поверхность.
- Для погодных данных используется внешний Open-Meteo API без управления ключами и учётными данными.
- Кеш локальный, с TTL 10 минут и верхним пределом 500 записей; сетевые данные проверяются на полноту и формат перед расчётами.
- Поиск оценивает кандидаты по худшему часовому фактору и ранжирует окна по уровню риска, числу факторов и времени начала. При равном уровне риска сравнение окон не объявляет победителя.

## Ограничения и проблемы

- Работа зависит от доступности Open-Meteo и сети; ошибки внешнего API обрабатываются контролируемо, но сами данные не гарантируются.
- Кеш не переживает перезапуск процесса и не разделяется между несколькими процессами.
- Часовой пояс ввода для этих инструментов не настраивается; преобразование использует фиксированное смещение UTC+3.
- Горизонт прогноза для оценки риска, поиска и сравнения погодных окон ограничен пятью сутками.
- Health endpoint опционален и доступен только при настройке `HEALTH_PORT`.
- Согласно существующему `weather-mcp/README.md`, Docker-сборка подготовлена, но ранее локально не подтверждалась. Это известное состояние, зафиксированное в README, а не результат текущей проверки.

## Дальнейшие шаги

- Возможное направление: сделать пороги риска и часовые пояса настраиваемыми.
- При необходимости нескольких экземпляров рассмотреть персистентный или общий кеш.
- Добавить наблюдаемость: метрики доступности внешнего API, задержек, ошибок и попаданий в кеш.
- Добавить Docker smoke-test и запуск проверок в CI; отдельно подтвердить сборку и health check контейнера.
- Рассмотреть контрактные интеграционные тесты с Open-Meteo через контролируемые ответы сервиса.
